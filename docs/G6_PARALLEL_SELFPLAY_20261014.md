# G6 自对弈并行化（2026-10-14）

## 为什么之前那么慢

两个原因叠在一起，第二个是主因。

### 1. 每一手棋本身很贵

单次决策要跑 32–64 次 PUCT 模拟，每次模拟展开一个新节点；
每个新节点要枚举约 36 条合法边（32 个筑墙候选 + 若干走子），
每条边算两次 `computerDistance`。
剖析结果（`training/profile-puct.cjs`，88.8 秒样本）：

| 函数 | 调用次数 | 总耗时 | 占比 |
|---|---|---|---|
| `computerDistance` | 457,632 | 62.9 s | 71% |
| `hellCandidates` | 6,144 | 25.4 s | 29% |

记忆化缓存把这部分砍半（见 [SEARCH_SPEEDUP_20261014.md](SEARCH_SPEEDUP_20261014.md)），
单局从 18.1 s 降到 7.3–7.9 s（32 模拟）。

### 2. 但真正的问题是：只用了 1 个核

本机 **24 个逻辑处理器**。串行驱动是单个 Node 进程，纯 CPU 密集、没有 IO 等待，
所以 23/24 的算力一直闲着。

自对弈是**天然可并行**的：局与局之间零依赖。
之前没并行纯粹是我第一版的实现疏漏。

## 并行的前提：每一局只依赖自己的编号

`training/g6-selfplay-core.cjs` 把"一局棋"抽成纯函数：

- 每局的随机源由 `(seed, gameIndex)` 推导 —— 同一编号永远同一张图、同一先手方；
- 每次搜索固定模拟次数（确定性模式），不看墙钟；
- 除 `engine` 的 ROCKS 外不读任何共享可变状态，而 ROCKS 每局都由同一张图重置。

因此**一局的输出只取决于它的编号**，不取决于执行顺序、机器快慢、或哪个进程跑的它。
这是能分片、还能保证结果一致的根本原因。

配套还发现一个有利性质：距离缓存每次 `setRocks` 都会清空，
所以**缓存本来就是"每局一份"的**，分片不会降低命中率。

## 结构

| 文件 | 职责 |
|---|---|
| `training/g6-selfplay-core.cjs` | 一局棋的完整逻辑，纯确定性 |
| `training/g6-map-bank.cjs` | 地图库加载 + 与评估库零重叠的前置审计 |
| `training/g6-selfplay-shard.cjs` | 跑一个连续编号区间，写独立文件，自带完成校验与跳过 |
| `training/g6-selfplay-parallel.cjs` | 规划分片、限定并发派生进程、按编号升序合并 |
| `training/g6-selfplay-puct-runner-v2.cjs` | 串行驱动，改为调用同一个 core |

分片数取 `workers × 4`，让长尾分片不至于拖慢整体。

## 验收：三种跑法必须逐字节相同

先把重构前代码产出的前 12 局冻结成对照组：

```
CONTROL-games0-12.jsonl   12 局 / 793 条样本
sha256 = 3a1eb72f4faf70739dca7a9a182e52a69cdbb5e42e99d56acbdbf7d0f02a9985
```

然后用三种方式各跑一遍同样的 12 局：

| 跑法 | sha256 前 16 位 | 结论 |
|---|---|---|
| 对照组（重构前） | `3a1eb72f4faf7073` | 基准 |
| 重构后串行 | `3a1eb72f4faf7073` | 逐字节相同 |
| 单分片（0–12） | `3a1eb72f4faf7073` | 逐字节相同 |
| **4 进程并行**（每片 1 局） | `3a1eb72f4faf7073` | 逐字节相同 |

同时证明了三件事：重构没改行为、分片没改行为、并行没改行为。

## 续跑语义

- 优先读进度文件并**校验整份产物的 sha256**；校验通过才信任其中的局数。
- 校验不通过（或没有进度文件）则退化为全量扫描：要求编号从 0 起连续，否则拒绝续跑。
- 合并时要求每个分片的 `sampleSha256` 与局数都对得上，且合并后必须是
  `0..target-1` 连续，否则直接抛错。
- 失败时已完成的**分片文件保留在磁盘上**，重跑即续。

## 实测：5.9 倍

正式批量：目标 1000 局，从第 227 局续跑，16 个进程，每片 13 局，共 60 片。

| 指标 | 数值 |
|---|---|
| 本次新建局数 | 773 |
| 实际墙钟 | **17.3 分钟** |
| 等价串行耗时（7.9 s/局） | 101.8 分钟 |
| **加速比（墙钟口径）** | **5.9x** |
| 总产出 | 1000 局 / 65,348 条样本 / 68.8 MB |
| 退化策略 / 非法动作 | 0 / 0 |
| 编号连续性 | 0–999 完整，进度文件 sha256 校验通过 |

### 为什么不是 16 倍

并行总加速 = `并发数 / 每进程变慢倍数`。实测每个进程在 16 路并发下单局从 7.9 s 变成
21.0 s（**变慢 2.66 倍**），所以 16 / 2.66 ≈ **6.0 倍**，与墙钟口径的 5.9x 吻合。

变慢的原因不是核不够：本机是 Intel Core Ultra 9 290HX Plus，**24 个物理核、24 线程**
（无超线程），频率 2.7 GHz，核是够的。真正的约束是**内存**：

```
总内存    15.4 GB
可用内存   1.5 GB   ← 关键
```

16 个 Node 进程各自持有 JS 堆、转置表与距离缓存，在只剩 1.5 GB 可用的情况下产生换页与
GC 压力。这意味着**加更多 worker 不会更好**，反而可能因为换页而变慢。

提高效率的方向因此是"让每个进程更省内存"（减小缓存上限、复用 Map），
而不是"开更多进程"。本次没有做这个调优。

### 一个反直觉的细节

分片数是 `workers × 4`，但每片 13 局 × ~285 s，所以每片本身就不短；
`workers × 4` 的作用是让最后一批不至于只跑 1 个进程，而不是让任务更小。
<100 局的小批量用并行反而更慢，因为每个进程都要重新加载并编译 1.5 MB 的引擎源码。

## 顺带用满样本复核了旧的偏差疑点

之前 55 局时发现 side 0 胜率偏高、但样本太小。现在 1000 局：

| 指标 | 数值 |
|---|---|
| side 0 胜 / side 1 胜 | 644 / 356 |
| side 0 胜率 | **64.4%**，z = 9.11 → 高度显著 |
| side 0 先行时 | side 0 胜 363 / side 1 胜 139（72%） |
| side 1 先行时 | side 1 胜 217 / side 0 胜 281（side 0 仍占优） |

**结论：这张棋盘对 side 0 存在真实的结构性优势，不是小样本噪声，也不是"先行权"造成的。**
side 0 即使后手也赢多。合理怀疑与两侧营地几何不对称有关（某一侧的出发点到对方营地更近）。

这对评测是硬要求：**任何候选对冠军的配对对战必须换手**，否则会被系统性高估。
项目现有评测脚本已经在做 seat 0/1 双跑，所以流程安全，但这个不对称应当单独查一次根因。

数据本身不受影响：value 目标是按"行棋方视角"标注的，所以座位优势会成为价值函数的一部分，
这是正确学习而不是污染。但**评估口径必须换手**。

## 仍然存在的天花板

并行只是把"1 个核"变成"16 个核"，**单局成本没有下降**。
要继续提速只有两条路，都不能在不动 `game.js` 的前提下做：

1. 优化 `hellWallAllowed → findPath`（每个节点 32 个候选 × 2 次寻路）——
   这两个函数是 `game.js` 内部的闭包引用，训练层拦不到。
2. 改搜索算法（限制墙候选、剪枝）——会改变落子语义，让全部历史基线与摘要作废。

所以并行是当前性价比最高的手段，但它不改变"10000 局需要多久"这个量级的本质，
只是把小时数除以核数。
